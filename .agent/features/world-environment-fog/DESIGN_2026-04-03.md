## Goal

Design a Cycles environment fog feature that behaves like a realtime, `aiFog`-style atmosphere:

- world-level effect
- camera-ray only
- direct-light only
- no GI, reflection, or refraction participation
- no HDRI / background lighting in v1
- additive atmosphere / emission-style result
- interactive enough to be useful during look development

This is intentionally **not** a true world volume implementation.

## Locked Requirements

- World-scoped feature, not a general object volume workflow.
- Direct lighting only.
- Camera rays only.
- Ignore HDRI / background contribution in v1.
- Keep Blender sun / distant lights in v1 as explicit scene lights.
- Emissive geometry is desirable, but only if it stays inside the cost envelope of existing Cycles
  emission sampling.
- Output should behave more like an atmosphere / additive emission layer than a full physical
  volume AOV system.

## What Both Research Tracks Agree On

- Arnold atmosphere behavior is the right product reference.
- A true world-volume path would be too heavy and too risky for v1.
- The best conceptual family is fake atmosphere / single-scatter direct-light fog.
- Realtime references consistently split into:
  - cheap height/depth fog
  - additive lighting fog
  - full froxel volumetrics
- For this feature, the middle category is the right target.

## Useful Additions From The Realtime Research

- Analytic single-scatter references are valuable for shaping the math and performance goals:
  - Sun et al., practical analytic single scattering
  - Dykeman's point-light fog integral
- Realtime engines often treat fog as a light-accumulation layer, not as full media transport.
- HG phase function and Beer-Lambert transmittance are cheap enough to use directly.
- Fixed-step sampling along a ray segment is often good enough when the step count is small and the
  effect is intentionally fake.

## Cycles-Specific Reality Checks

### Emissive Geometry Is Not Just Another `KernelLight`

- Explicit lights live in the light array.
- Emissive geometry is sampled through the light distribution or light tree path.
- That means "loop over `num_lights` and include emissive triangles" is not a correct assumption.
- If v1 includes emissive geometry, it should do so by reusing existing Cycles emitter sampling
  logic, not by inventing a second fake emitter list.

### Background / HDRI Is Already Separable

- Background evaluation and background MIS are already split from ordinary light-object sampling.
- Excluding HDRI in v1 is straightforward in product terms and aligns with Arnold.

### Eevee Should Not Drive The Architecture

- Eevee has world-volume and probe-specific logic, including special sunlight handling.
- It is a useful reference for behavior, but not the right implementation model for this Cycles
  feature.

## Rejected Design Assumptions

### Reject: Full World Volume For V1

- Too much integrator surface area.
- High regression risk.
- Wrong mental model for a fake atmosphere effect.

### Reject: Froxel Architecture For V1

- Strong realtime reference, but too large and invasive for the current branch goal.

### Reject: Background-Only Fog

- The effect needs to accumulate between camera and surfaces as well.
- Otherwise it becomes a sky treatment, not atmosphere.

### Reject: "Emissive Geometry Is Free"

- It is already supported in Cycles sampling terms, but cost scales with emitter complexity.
- V1 must explicitly rely on existing emission-sampling eligibility and Light Tree scalability.

## Viable Architecture Options

### Option A: Dedicated Environment Fog Integrator Stage

- Add a world-only fog definition.
- Evaluate fog as a separate atmosphere pass along the camera segment.
- Reuse existing direct-light sampling concepts where possible.
- Keep the feature logically separate from true world volume transport.

Pros:
- Closest to the requested product behavior.
- Clear mental model.
- Lowest risk of breaking real volume behavior.

Cons:
- Needs new pass-routing rules.
- Needs careful design for how emitters are sampled without duplicating too much logic.

### Option B: Special-Case Fake Volume Closure

- Route fog through a constrained world-volume-like path.
- Suppress indirect and non-camera behavior aggressively.

Pros:
- May reuse more existing volume machinery and pass semantics.

Cons:
- Easier to accidentally inherit the cost and complexity of real volume transport.
- Harder to keep the feature obviously fake and responsive.

### Option C: Screen / Mist Hybrid

- Cheap depth-plus-height fog with some light injection.

Pros:
- Fastest path.

Cons:
- Too far from the requested renderer-native atmosphere feature.

## Recommended Architecture

Choose **Option A**.

### Product Shape

- World-only `Environment Fog` feature.
- Camera-ray only.
- Direct-light only.
- No HDRI / background in v1.
- Sun / distant lights allowed.
- Emissive geometry allowed only through existing Cycles emission-sampling eligibility.
- Additive atmosphere / emission-style output first.

### Rendering Model

For the camera segment from the camera to the first hit, or camera to background if there is no
hit:

- evaluate fog over the segment
- accumulate light contribution from explicit scene lights
- optionally accumulate eligible emissive geometry if sampling cost is acceptable
- do not spawn indirect fog paths
- do not use full world-volume transport

This should be treated as **single-scatter atmosphere accumulation**, not as a general volume.

## Recommended Numerical Strategy

Use a small fixed-step integration over the camera segment for v1.

Why:

- simpler and safer than trying to land multiple closed-form integrals for different light types
- keeps HG phase and transmittance straightforward
- easier to debug and compare visually
- easier to clamp and optimize for interactivity

What this means:

- local-light and sun-light handling can share one integration framework
- later optimization can replace specific light classes with analytic shortcuts if needed

## Recommended Cycles Integration Strategy

### World Definition

- Define fog as a world-level feature, not a material feature.
- Keep it separate from true world volume behavior in product semantics.

### Integrator Placement

- Evaluate fog on camera rays for:
  - camera to first surface hit
  - camera to background
- Do not evaluate it for reflection, refraction, diffuse bounce, or transmission paths.

### Light Sources

- Include:
  - point lights
  - spot lights
  - area lights
  - distant / sun lights
- Exclude:
  - background / HDRI
- Conditionally include:
  - emissive geometry already eligible for Cycles emission sampling

### Pass Strategy

V1 should prioritize:

- Combined contribution
- Fog-specific additive / emission-style output semantics

Do not block v1 on full per-light AOV support.

If light identity can be preserved cheaply in the fog accumulation path, light-AOV splitting is a
strong v2 extension.

## Emissive Geometry Policy

Recommended v1 rule:

- only include emissive geometry that already participates in Cycles emission sampling
- strongly prefer Light Tree when emissive geometry is dense
- document that heavy emissive scenes may need emission sampling trimmed for interactivity

This keeps the feature aligned with existing Cycles cost controls instead of introducing a parallel
performance model.

## Performance Guardrails

- Low default integration step count.
- Camera-ray only.
- No volumetric shadowing in v1 unless profiling proves it is cheap enough.
- No HDRI contribution.
- No indirect transport.
- Reuse existing emitter eligibility rules instead of widening the emitter domain.

## Blocking And Holdout Behavior

### Two Different Kinds Of "Blocking"

1. Camera-side blocking
   - Fog should only accumulate from the camera to the first visible hit.
   - If geometry, including holdout geometry, is hit first, fog behind that hit should not keep
     accumulating on the same camera ray.
   - This is required for normal compositing correctness and holdout workflows.
   - This is comparatively cheap.

2. Light-side blocking
   - Fog samples should only receive light if the path from the sample point to the light is not
     occluded by scene geometry.
   - This is true volumetric shadowing.
   - This is expensive because it introduces light-occlusion work inside the fog evaluation loop.

### V1 Decision

- V1 must support **camera-side blocking**.
- V1 should be **holdout-aware**, meaning holdout hits stop further fog accumulation behind them on
  the camera path.
- V1 does **not** need full light-side object shadowing.

### Why This Split Matters

- It preserves holdout and matte workflow correctness without turning the feature into a costly
  shadowed-volume system.
- It keeps the implementation aligned with the "fake atmosphere" goal.
- It avoids conflating compositing correctness with volumetric shadow quality.

## Open Decisions Still Worth Locking

1. How should the world-level UI be exposed?
   - dedicated world-only shader node
   - world settings panel backed by Cycles properties
   - hybrid approach

2. What is the v1 pass surface?
   - combined only
   - combined plus dedicated fog pass
   - combined plus reuse of emission semantics

3. Is volumetric shadowing explicitly out for v1?
   - current recommendation: yes for light-side shadowing
   - camera-side blocking and holdout-aware clipping are in for v1

4. Is height fog in v1 or v2?
   - current recommendation: keep the implementation extensible, but do not let height behavior
     block a uniform-density v1

## Current Recommendation To Carry Forward

Build a **world-only, camera-ray-only, direct-light-only environment fog feature** that behaves as
an additive atmosphere effect, excludes HDRI, includes sun lights, and reuses existing Cycles
emitter eligibility for emissive geometry.

This is the best overlap between:

- Arnold-like product expectations
- realtime shader design patterns
- Cycles' actual current lighting architecture
- the branch goal of staying interactive and low-risk
