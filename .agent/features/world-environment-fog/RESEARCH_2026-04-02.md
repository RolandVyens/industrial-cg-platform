## Existing Blender And Cycles Hooks

### Existing World Mist Is Not The Target Feature

- Cycles already syncs world mist start/depth/falloff into film settings in
  `intern/cycles/blender/sync.cpp`.
- This is a render pass / depth-fade control, not an interactive lit fog system.
- Blender manual language also frames Mist as a depth map for compositing, not a participating
  medium.

### Direct Light Sampling Already Covers Lights And Emissive Geometry

- Cycles surface direct lighting uses `light_sample_from_position(...)` from
  `intern/cycles/kernel/integrator/shade_surface.h`.
- Emissive surfaces are accumulated separately in `integrate_surface_emission(...)` in the same
  file.
- The light manager builds the direct-light distribution from both enabled light objects and
  emissive triangles in `intern/cycles/scene/light.cpp`.
- This is the strongest existing hook for an interactive fog feature that should react to scene
  lighting without requiring a full world-volume rewrite.

### Emissive Geometry Is Already Sampled, But Cost Needs Guardrails

- Cycles already includes emissive triangles in direct-light sampling when
  `shader->emission_sampling != EMISSION_SAMPLING_NONE`.
- Without light tree, `intern/cycles/scene/light.cpp` explicitly counts emissive triangles and
  warns that too many emissive triangles should push the user toward Light Tree or disabling
  emission sampling on some materials.
- Shader-side `EMISSION_SAMPLING_AUTO` already disables weak emitters automatically based on the
  emission estimate in `intern/cycles/scene/shader.cpp`.
- Design implication:
  - emissive geometry can be included in v1 without inventing a new sampling system
  - v1 should only use emissive geometry that is already eligible for Cycles emission sampling
  - feature docs and UI should warn that many emissive triangles are cheapest with Light Tree on

### Background / HDRI Lighting Is A Separate Path

- Background shading is evaluated in `intern/cycles/kernel/integrator/shade_background.h`.
- World MIS and HDRI sampling are prepared separately in `intern/cycles/scene/light.cpp`.
- This means a v1 fog feature can choose to:
  - include background/HDRI contribution
  - exclude background/HDRI contribution
  - make that behavior a toggle
  without disturbing mesh-emission or local-light sampling.

### Eevee Has Different Constraints

- Eevee stores world lighting through an internal light-probe path rather than matching Cycles'
  world evaluation exactly.
- Eevee also has explicit world-volume handling and special sunlight extraction behavior.
- If the VFX branch feature is implemented in Cycles first, Eevee parity should be treated as
  follow-up work, not a v1 requirement.

## External Renderer Research

### Arnold

- Arnold's `aiFog` / atmosphere workflow is configured as an atmosphere shader in render settings.
- Arnold docs describe atmosphere shaders as special volume shaders assigned in render settings
  under Environment > Atmosphere.
- Arnold light path expression docs provide a strong AOV reference point:
  - `emission` is `C[LO]`
  - `background` is `CB`
  - `volume_direct` is `CVL`
  - `volume_indirect` is `CV[DSVOB].*`
- This makes the user goal more concrete: the requested fog behavior is closer to an additive
  atmosphere or emission-style result than to a fully path-traced volume AOV breakdown.
- Arnold `atmosphere_volume` is scene-wide and supports shafts / volumetric shadows, but Autodesk's
  docs explicitly say it works with point, spot, and area lights, not distant or skydome lights.
- This is a useful precedent for a feature that is intentionally selective about which lighting
  sources influence fog.

### Maya envFog

- Maya `envFog` is scene-wide and exposes start/end distance, near/far distance, height controls,
  color, density, and scatter controls.
- It is a good UI reference for artist-friendly distance and height controls even though it is not
  the Cycles target implementation.

### Redshift

- Redshift's Environment / Volumetric Scattering docs frame global fog as an environment-level
  effect rather than a localized volume.
- Redshift exposes ray contribution scales for camera, reflection, GI, and environment-fog rays.
- GI contribution is documented as disabled by default because it is expensive and can wash out the
  result.
- This is a strong precedent for keeping v1 focused on direct / camera-visible behavior first and
  making broader ray participation optional.

### V-Ray

- V-Ray Environment Fog simulates participating media scene-wide.
- Official docs say it scatters light from all scene light sources by default.
- V-Ray also exposes controls for GI scattering and for restricting affected lights.
- This is the clearest precedent for an artist-facing "all lights by default, but selective if
  needed" environment fog model.

### Unity

- Unity HDRP Fog is a Volume override with optional volumetric fog, evaluated on a low-resolution
  3D grid in the camera frustum.
- Unity HDRP docs emphasize that fog interacts with scene lighting, but also document reprojection
  and quality limitations.
- Open-source Unity implementations split into two useful families:
  - froxel / raymarch systems inspired by Wronski and Frostbite
  - lightweight analytic or screen-space fog shaders that sit on top of existing lighting
- `Unity-Technologies/VolumetricLighting` is especially relevant because it supports constant and
  height-based density, anisotropy, and multiple light classes while openly accepting practical
  approximations.
- `SlightlyMad/VolumetricLights` is also relevant because it treats volumetric lighting as an
  additive effect over existing lighting buffers rather than as a physically complete volume path.
- In the Chinese Unity community, common custom URP solutions are not full volumetric systems:
  they are usually depth fog, height fog, or renderer-feature / post-process hybrids.
- This is a useful reminder that an interactive, art-directable approximation is often more useful
  in practice than a fully physical but heavy solution.

### Unreal Engine

- Unreal splits Exponential Height Fog, Local Fog Volumes, and Volumetric Fog into related but
  distinct systems.
- Official Unreal docs note that Volumetric Fog does not support all Exponential Height Fog
  controls because the older height-fog model is non-physical.
- Unreal docs also describe Sky Atmosphere and Exponential Height Fog as additive / cooperating
  systems.
- Chinese UE developers often analyze the froxel-grid + front-to-back integration path and
  Frostbite-inspired implementation details, which reinforces that full volumetric pipelines are
  materially more expensive than height / distance fog approximations.

## Chinese Developer Community Findings

### Unity / URP

- A recurring pattern in Chinese Unity posts and plugins is:
  - depth fog
  - height fog
  - renderer feature injection
  - limited light support added incrementally
- Community plugins for URP volumetric lighting commonly support main light plus additional lights,
  then layer shadows and mixed lights on top.
- This suggests a practical v1 should define exactly which light classes are supported first rather
  than promising "all Cycles lighting behavior" from day one.

### Unreal

- Chinese UE articles frequently focus on source analysis of volumetric fog froxel grids, temporal
  reprojection, and raymarch / integration stages.
- The takeaway is not that Cycles should copy UE's froxel architecture, but that "interactive fog"
  and "true volumetric fog" quickly diverge in implementation cost.

## Papers And Open-Source Shader References

### Analytic And Approximate Models

- Sun et al., "A Practical Analytic Single Scattering Model for Real-time Rendering" is a strong
  reference for approximating single scattering with a much simpler interface than full
  participating media.
- Isaac Dykeman's "A Simple Shader for Point Lights in Fog" is especially relevant for a
  direct-light-only v1 because it derives a closed-form integral for point lights along the view
  ray and suggests summing multiple lights in a deferred pipeline.
- These references support a design where fog is evaluated as an interactive lighting effect rather
  than as a full multiple-scattering medium.

### Froxel And Unified Volumetric Systems

- Bart Wronski's volumetric fog work is the canonical real-time froxel reference.
- Frostbite's unified volumetric rendering work extends that approach with physically based
  parameterization and broader engine integration.
- These are valuable architectural references, but they are probably too large for the intended
  `aiFog`-like Cycles v1 if the goal is a fake atmosphere shader rather than a full world volume.

### Open-Source Engines And Repos

- `Unity-Technologies/VolumetricLighting`
  - supports constant and height fog style controls
  - handles multiple light classes
  - is explicit about approximations
- `SlightlyMad/VolumetricLights`
  - supports directional, point, and spot lights
  - adds volumetric contribution into the renderer's existing lighting results
- `diharaw/volumetric-fog`
  - clean OpenGL sample for a Wronski-style volumetric fog implementation
- Godot fog shader docs are a useful semantic reference because fog outputs are explicitly split
  into `ALBEDO`, `DENSITY`, and `EMISSION`, with emission added during the light pass

## Realtime Shader Design Patterns

### Pattern 1: Additive Light Buffer Injection

- Example: `SlightlyMad/VolumetricLights`
- Design:
  - allocate a dedicated volumetric light buffer
  - render only lights that opt into the effect
  - raymarch or integrate inside each light volume
  - blur and upsample
  - add the result into the renderer's existing light buffer
- Why it matters:
  - the fog is treated as a lighting add-on, not as a general-purpose medium
  - this maps well to the requested `aiFog`-like "fake volume shader" goal

### Pattern 2: Froxel Volume With Light Injection

- Examples: Unity Adam VolumetricLighting, Wronski, Frostbite, Godot fog volumes
- Design:
  - store density / scattering state in a frustum-aligned 3D grid
  - inject direct lights into the grid
  - resolve the grid along camera rays
- Why it matters:
  - this is the standard modern realtime volumetric architecture
  - it is powerful, but likely too large for the intended Cycles v1

### Pattern 3: Analytic Camera-Ray Integral Per Light

- Example: Isaac Dykeman's point-light fog shader
- Design:
  - derive a closed-form or near-closed-form integral for light scattering along the camera ray
  - sum contributions only for nearby or relevant lights
- Why it matters:
  - aligns naturally with "camera ray only"
  - avoids a full volumetric data structure
  - is the best conceptual match for an inexpensive `aiFog`-like direct-light-only implementation

### Pattern 4: Depth / Height Fog Post Effect

- Example: `meryuhi/URPFog`
- Design:
  - fullscreen pass using depth, distance, height, and optional noise
  - no true light transport
- Why it matters:
  - very cheap
  - useful as a baseline for artist controls and performance expectations
  - insufficient on its own for the requested interactive-lighting behavior

## Updated Design Read

- The requested feature now reads as:
  - `aiFog`-like
  - direct-light only
  - fully interactive
  - fake volume shader rather than a true world medium
  - camera ray only
  - emissive geometry included when it is already cheap enough under Cycles emission sampling
  - HDRI / background excluded for v1
  - Blender sun / distant lights included for v1 as explicit scene lights
  - default output closer to an additive atmosphere / emission-style contribution than to classic
    volume light AOVs
  - optional light AOV splitting would be useful if it falls out naturally from the architecture

## Implementation Approaches

### Approach A: True World Volume

- Add a real world participating medium path that behaves like a proper infinite volume.
- Pros:
  - most physically grounded
  - naturally fits volume lighting concepts
  - easier to explain in renderer terms
- Cons:
  - much larger kernel / integrator surface area
  - more risk to world-volume, shadowing, and pass behavior
  - much heavier than the feature intent

### Approach B: Dedicated Environment Fog Integrator Path

- Add a world-only fog node and evaluate a dedicated fog contribution for rays traveling through
  empty space, sampling existing light distributions and background as chosen by feature settings.
- Pros:
  - aligns with "interactive lighting" goal
  - can reuse current direct-light and emission infrastructure
  - keeps scope narrower than full world-volume support
  - can expose artist-friendly controls similar to aiFog / envFog
- Cons:
  - not fully physical
  - needs clear rules for which rays and passes receive fog
  - requires careful integration with background, emissive meshes, and AOVs

### Approach B2: Fake Fog As Special-Case Volume Closure

- Represent fog internally as a constrained world-volume-like closure, but limit it to
  single-scattering direct-light evaluation and suppress full volume transport behavior.
- Pros:
  - might reuse more existing volume pass and light AOV machinery
  - could make optional split into volume or light AOVs easier
- Cons:
  - higher risk of accidental interaction with real volume logic
  - harder to keep conceptually "fake" and interactive

### Approach C: Mist / Post Composite Approximation

- Extend Mist-like depth behavior with color / height controls.
- Pros:
  - cheapest
  - minimal kernel risk
- Cons:
  - does not satisfy interactive lighting goal
  - no real response to lights or emissive geometry
  - too far from the intended feature

## Recommended Direction

- Choose **Approach B** for v1.
- Recommended v1 behavior:
  - world-only node, not a generic material node
  - artist-friendly controls: color, density, start distance, max distance, base height,
    height falloff, anisotropy optional
  - use existing direct-light infrastructure so local lights and eligible emissive geometry can
    influence fog
  - include emissive geometry only when it is already enabled for Cycles emission sampling, and
    rely on Light Tree for scalability
  - keep HDRI / background out for v1
  - keep Blender sun / distant lights in for v1 as explicit scene lights
  - keep indirect / GI fog contribution off or limited by default, following Redshift's practical
    precedent
  - route default fog output like an atmosphere / emission-style result first
  - treat light AOV split as an optional extension if we can preserve light identity cheaply during
    fog evaluation

## Refined Cycles Design Candidate

### Candidate V1

- Evaluate fog only for camera rays.
- Do not make fog participate in reflection, refraction, or indirect transport.
- Treat fog as a dedicated world effect, not as a true world volume.
- Accumulate fog from the existing direct-light sampling domain:
  - local lights
  - distant / sun lights
  - no background / HDRI
  - emissive geometry only when already eligible for emission sampling
- Write the result into combined plus a fog/emission-style channel or pass.

### Why This Candidate Fits The Research

- Matches Arnold's atmosphere mindset better than a physically complete world volume.
- Matches practical realtime implementations that treat fog as an additive lighting layer.
- Reuses Cycles' current emitter selection instead of inventing a second lighting universe just for
  fog.
- Keeps the camera-ray-only promise, which is the strongest simplifier discovered in the design
  discussion so far.

## Design Questions To Lock Before Coding

1. Should the node live only in the World shader tree, or should it also be available in material
   graphs for future reuse?
2. Should emissive geometry be included in v1 direct-light fog evaluation, or only explicit light
   objects plus background?
3. Should background / HDRI contribution be always on, always off, or exposed as a toggle?
4. Should reflection / transmission rays receive fog in v1, or only camera rays?
5. Should v1 expose a dedicated fog AOV, or should it reuse emission / volume semantics first?
